# Личная CRM

Контакты людей, которых знаю лично: кто это, откуда знакомы, телефон, почта и заметки о разговорах.

## Как запустить

Нужны: Docker Desktop, Node.js 20 или новее и pnpm.

### База данных (PostgreSQL в Docker)

1. Если файла `.env` ещё нет: скопируйте `.env.example` в `.env` и заполните значения
2. Запустите базу: `docker compose up -d`
3. Проверьте статус: `docker compose ps`. В колонке STATUS должно быть `healthy`

Остановить базу: `docker compose stop`. Данные при этом сохраняются.

Осторожно: `docker compose down -v` удаляет базу вместе со всеми данными.

### Приложение

Первый запуск:

1. Установите зависимости: `pnpm install`
2. Создайте таблицы в базе: `pnpm db:migrate`
3. По желанию — заполните базу тестовыми данными (1000 контактов с заметками): `pnpm db:seed`.
   Примерно у трети контактов задано, как часто общаться, поэтому на главной сразу виден блок «Пора связаться».
   Если в базе уже есть контакты, команда ничего не добавит
4. Запустите приложение: `pnpm dev`
5. Откройте в браузере http://localhost:3000

В следующие разы достаточно запустить базу (`docker compose up -d`) и приложение (`pnpm dev`).
Остановить приложение: нажать `Ctrl+C` в окне терминала, где оно запущено.

Приложение открывается только на этом компьютере: из локальной сети его не видно — так же, как и базу.

Подключение к базе приложение берёт из `.env`: из тех же `POSTGRES_*`, что использует Docker
(или из `DATABASE_URL`, если она задана).

## Как проверить, что всё работает

1. Откройте http://localhost:3000 — видно список всех контактов, сверху счётчик «Всего …»
2. Нажмите «Добавить контакт», заполните имя и сохраните — вас вернёт к списку, новый контакт подсвечен зелёным
3. Начните вводить его имя в поиске — список сократится до найденных
4. Откройте карточку, напишите заметку и нажмите «Добавить заметку» (или ⌘/Ctrl + Enter) — заметка появится ниже с датой
5. Обновите страницу или откройте тот же адрес в другом браузере — контакт и заметка на месте
6. В карточке нажмите «Изменить», внизу — «Удалить контакт». В окне видно, сколько заметок удалится вместе с ним. Нажмите «Удалить» — вас вернёт к списку с сообщением «Контакт … удалён», в списке его больше нет

## Выкатка на сервер

Приложение работает на https://app.example-crm.site. Новая версия выкатывается сама после каждого push в ветку `main`:

1. GitHub Actions собирает образ приложения и кладёт его в GitHub Container Registry (GHCR) с тегом — хешем коммита. Ход видно на GitHub во вкладке Actions → Deploy
2. GitHub копирует папку `deploy/` на сервер и запускает там `deploy.sh`
3. Сервер скачивает образ и отдельным разовым контейнером из него применяет миграции базы. Упали миграции — новая версия не запускается, работает прежняя
4. Сервер запускает новую версию и проверяет `/health`
5. В конце GitHub открывает https://app.example-crm.site/health снаружи и сверяет версию

Если какой-то шаг упал, выкатка в Actions краснеет, и GitHub присылает письмо. Сам сервер ничего не откатывает: решаете вы, см. «Откат».

Какая версия сейчас работает: откройте https://app.example-crm.site/health — поле `commit` совпадает с последним коммитом в `main`.

На сервере приложение и его база — проект docker compose `prod` в папке `/srv/prod`. У сервера своя база, отдельная от базы на вашем компьютере. Образы на сервере хранятся только для текущей и предыдущей версий, логи — не больше 30 МБ на контейнер.

Что где:

- `Dockerfile` — как собирается приложение
- `.github/workflows/deploy.yml` — шаги в GitHub Actions: сборка, GHCR, вызов `deploy/ci-deploy.sh`
- `deploy/ci-deploy.sh` — копирует `deploy/` на сервер, запускает выкатку и проверяет адрес снаружи
- `deploy/deploy.sh` — выкатка на стороне сервера, откат и состояние
- `deploy/compose.yaml` — приложение и его база на сервере
- `deploy/setup-server.sh` — подготовка сервера, запускаете вы с паролем sudo

### Команды на сервере

Вставлять в Терминал на Mac. Каждая просит пароль sudo: символы при вводе не видны, это нормально.

- Состояние: `ssh -t crm sudo -u crmdeploy bash /srv/prod/deploy/deploy.sh status`
- Тестовые данные в пустую базу: `ssh -t crm sudo -u crmdeploy bash /srv/prod/deploy/deploy.sh seed`
- Настройки базы лежат в `/srv/prod/.env`, прочитать их может только пользователь crmdeploy: `ssh -t crm sudo -u crmdeploy nano /srv/prod/.env`

### Откат

Только вручную. Команда запускает версию, которая работала до последней выкатки, — её образ хранится на сервере:

```
ssh -t crm sudo -u crmdeploy bash /srv/prod/deploy/deploy.sh rollback
```

Миграции базы при откате не отменяются: прежняя версия продолжает работать с новой схемой базы.

### Копии базы

Перед изменениями на сервере `setup-server.sh` сохраняет копию базы в `/var/backups/personal-crm/`. Прочитать её может только root.

### Подготовка сервера

Файлы из `deploy/` выкатка копирует на сервер сама. Но пользователей, права и nginx настраивает только `setup-server.sh`, и запускаете его вы — первый раз и когда этот файл поменялся:

```
scp deploy/* crm:crm-app-setup/
ssh -t crm sudo bash crm-app-setup/setup-server.sh
```

GitHub заходит на сервер своим ключом как пользователь crmdeploy. Ключ лежит в секретах репозитория (Settings → Secrets and variables → Actions: `DEPLOY_SSH_KEY`, `DEPLOY_KNOWN_HOSTS`, `DEPLOY_HOST`). crmdeploy может копировать файлы и запускать Docker, а это уровень root на сервере. Поэтому ключ хранится только в секретах GitHub.

## Для разработки

- `pnpm build` и `pnpm start` — собрать и запустить «боевую» версию (быстрее, чем `pnpm dev`)
- `pnpm lint` — проверка кода
- `pnpm db:generate` — создать миграцию после изменения схемы в `src/db/schema.ts`
- `pnpm db:migrate` — применить миграции к базе
