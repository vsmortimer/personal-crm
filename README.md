# Личная CRM

Контакты людей, которых знаю лично: кто это, откуда знакомы, телефон, почта и заметки о разговорах.

## Как запустить

Нужны: Docker Desktop, Node.js 20 или новее и pnpm.

### База данных (PostgreSQL) и почтовая заглушка (Mailpit) в Docker

1. Если файла `.env` ещё нет: скопируйте `.env.example` в `.env` и заполните значения. Строки для входа - в разделе «Вход на своём компьютере» ниже
2. Запустите базу и почтовую заглушку: `docker compose up -d`
3. Проверьте статус: `docker compose ps`. У базы (`db`) в колонке STATUS должно быть `healthy`, у заглушки (`mail`) - `Up`

Остановить обе: `docker compose stop`. Данные базы при этом сохраняются.

Осторожно: `docker compose down -v` удаляет базу вместе со всеми данными.

### Вход на своём компьютере

В приложение входят по ссылке из письма, паролей нет. На вашем компьютере письма никуда не уходят: их ловит Mailpit, и читать их можно на странице http://localhost:8025. Так можно войти под любой почтой, например `friend@example.com`, и проверить, что видит другой человек.

Добавьте в `.env` пять строк (и такие же ключи, но без значений, в `.env.example`):

```
BETTER_AUTH_SECRET=случайная строка
BETTER_AUTH_URL=http://localhost:3000
SMTP_URL=smtp://127.0.0.1:1025
MAIL_FROM="Личная CRM <noreply@mail.crm.app.example-crm.site>"
OWNER_EMAIL=ваша почта
```

- `BETTER_AUTH_SECRET` - случайная строка, которой приложение подписывает вход. Получить её: `openssl rand -base64 32`, результат вставьте после знака `=`. Никому не показывайте
- `BETTER_AUTH_URL` - адрес, по которому вы открываете приложение. Ссылка в письме ведёт именно на него, поэтому открывайте приложение по этому же адресу: `localhost` и `127.0.0.1` для браузера разные сайты, вход на одном не виден на другом
- `SMTP_URL` - куда отправлять письма. `smtp://127.0.0.1:1025` - Mailpit из Docker. Если здесь окажется что-то другое, приложение отправит настоящие письма
- `MAIL_FROM` - от кого письма
- `OWNER_EMAIL` - ваша настоящая почта. Все контакты, заметки и группы, которые были в базе до входа, достаются пользователю с этой почтой. Демо-данные (`pnpm db:seed`) тоже создаются у него

### Приложение

Первый запуск:

1. Установите зависимости: `pnpm install`
2. Создайте таблицы в базе: `pnpm db:migrate`.
   Если в базе уже есть контакты, нужна строка `OWNER_EMAIL` в `.env`: контакты достанутся этому пользователю. Без неё команда остановится с ошибкой `OWNER_EMAIL is not set`, ничего не изменив. В пустой базе строка не нужна
3. По желанию — заполните базу тестовыми данными (1000 контактов с заметками): `pnpm db:seed`.
   Данные создаются у пользователя с почтой `OWNER_EMAIL`: войдите под ней, чтобы их увидеть, а под другой почтой список будет пустым.
   Примерно у трети контактов задано, как часто общаться, поэтому на главной сразу виден блок «Пора связаться».
   Примерно половина контактов разложена по группам «Семья», «Друзья», «Знакомые», «Теннис» и «Аналитики», поэтому на главной сразу виден фильтр по группам.
   Если у этого пользователя уже есть контакты, команда ничего не добавит
4. Запустите приложение: `pnpm dev`
5. Откройте в браузере http://localhost:3000 (тот адрес, что в `BETTER_AUTH_URL`): откроется страница входа. Введите почту, нажмите «Получить ссылку», откройте http://localhost:8025, письмо «Вход в Личную CRM» - в нём кнопка «Войти»

В следующие разы достаточно запустить базу (`docker compose up -d`) и приложение (`pnpm dev`).
Остановить приложение: нажать `Ctrl+C` в окне терминала, где оно запущено.

Приложение открывается только на этом компьютере: из локальной сети его не видно — так же, как и базу.

Подключение к базе приложение берёт из `.env`: из тех же `POSTGRES_*`, что использует Docker
(или из `DATABASE_URL`, если она задана). Настройки входа и почты - оттуда же, см. «Вход на своём компьютере».

## Как проверить, что всё работает

1. Откройте http://localhost:3000 — страница входа. Введите свою почту (ту, что в `OWNER_EMAIL`), нажмите «Получить ссылку», откройте письмо на http://localhost:8025 и нажмите в нём «Войти». Видно список ваших контактов, сверху счётчик «Всего …», в шапке справа ваша почта и «Выйти»
2. Нажмите «Добавить контакт», заполните имя и сохраните — вас вернёт к списку, новый контакт подсвечен зелёным
3. Начните вводить его имя в поиске — список сократится до найденных
4. Откройте карточку, напишите заметку и нажмите «Добавить заметку» (или ⌘/Ctrl + Enter) — заметка появится ниже с датой. Скопируйте адрес карточки из адресной строки: он понадобится в шаге 7
5. Обновите страницу или откройте тот же адрес в другом браузере и войдите под той же почтой — контакт и заметка на месте
6. В карточке нажмите «Изменить», внизу — «Удалить контакт». В окне видно, сколько заметок удалится вместе с ним. Нажмите «Удалить» — вас вернёт к списку с сообщением «Контакт … удалён», в списке его больше нет
7. Проверьте, что чужого не видно. Нажмите «Выйти», войдите под другой почтой, например `friend@example.com` (письмо — на http://localhost:8025): список пустой, «Контактов пока нет» и «Добавь первый контакт». Вставьте в адресную строку адрес карточки из шага 4: «Контакт не найден». Выйдите и войдите под своей почтой — всё на месте

## Тесты

Тесты проверяют серверную часть и логику форм на настоящей базе PostgreSQL и настоящей почтовой заглушке Mailpit в Docker: письма со ссылками для входа уходят в Mailpit, тесты читают их оттуда.

1. Запустите базу и Mailpit: `docker compose up -d`
2. Запустите тесты: `pnpm test`

В конце должно быть написано `passed` и не должно быть `failed`.

Тесты сами создают отдельную базу — с тем же именем, что рабочая, и окончанием `_test` — и удаляют её после прогона. Рабочую базу на вашем компьютере они не трогают.

Если база не запущена, тесты остановятся с подсказкой `docker compose up -d db`, если не запущен Mailpit - с подсказкой `docker compose up -d mail`. Письма из тестов настоящим людям не уходят: тесты откажутся запускаться, если `SMTP_URL` ведёт не на этот компьютер.

### Сквозные тесты (e2e)

Проходят сценарии так, как их проходит человек: настоящий браузер входит по ссылке из письма (письмо берёт из Mailpit), открывает список контактов, добавляет контакт, находит его поиском, пишет заметку и проверяет, что она сохранилась — после обновления страницы и в другом браузере, который ничего не знает о первом. Отдельный тест проверяет, что двое людей в двух браузерах не видят данные друг друга.

Первый раз установите браузер для тестов (около 200 МБ на диске): `pnpm exec playwright install --only-shell chromium`

1. Запустите базу и Mailpit: `docker compose up -d`
2. Запустите тесты: `pnpm test:e2e`

В конце должно быть написано `passed` и не должно быть `failed`.

Тесты сами собирают «боевую» версию приложения и запускают её на http://127.0.0.1:3100 — отдельно от `pnpm dev` на порту 3000, его останавливать не нужно. База у них тоже своя — с окончанием `_e2e_test`: тесты создают её перед прогоном и удаляют после. Рабочую базу они не трогают.

Если тест упал, откройте отчёт со снимком экрана в момент ошибки: `pnpm exec playwright show-report`. Закрыть отчёт: `Ctrl+C` в окне терминала.

## Проверки в pull request (CI)

Изменения попадают в `main` только через pull request (PR). На каждый PR GitHub Actions запускает проверки из `.github/workflows/ci.yml`:

- **Lint** — проверка кода: `pnpm lint`
- **Format** — код отформатирован Prettier: `pnpm format:check`. Исправить: `pnpm format`
- **Types** — проверка типов TypeScript: `pnpm typecheck`
- **Vitest** — тесты, см. «Тесты»
- **Playwright** — сквозные тесты, см. «Сквозные тесты (e2e)»
- **Image** — образ приложения собирается так же, как при выкатке, но никуда не отправляется

Базу и почтовую заглушку для тестов GitHub создаёт на время проверки и удаляет после: ни базу на вашем компьютере, ни сервер проверки не трогают, настоящие письма не уходят.

Ход проверок виден внизу страницы PR. Если упали сквозные тесты, отчёт со снимками экрана лежит на странице прогона: Summary → Artifacts → `playwright-report`. Скачайте, распакуйте и откройте командой `pnpm exec playwright show-report <папка>/playwright-report`.

Защита ветки `main` на GitHub (Settings → Branches):

- писать в `main` напрямую нельзя никому, в том числе владельцу, — только через PR
- PR вливается, только когда все шесть проверок зелёные и ветка PR не отстаёт от `main`. Отстаёт — на странице PR нажмите «Update branch», проверки пройдут заново
- автовлитие: PR, у которого оно включено, вливается сам (squash), как только проверки позеленеют. Сразу после этого начинается выкатка

Prettier не трогает тексты в Markdown (`*.md`) и файлы, которые пишут инструменты (`pnpm-lock.yaml`, `drizzle/`, `.claude/`, `openspec/`), см. `.prettierignore`.

## Выкатка на сервер

Есть два окружения, у каждого свои база, `.env` и ключи:

- **прод** — https://app.example-crm.site, настоящие данные
- **тест-стенд** — https://test-app.example-crm.site, закрыт паролем, база — копия данных прода. Подробности — в разделе «Тест-стенд» ниже

Merge в `main` выкатывает только тест-стенд. **Прод выкатываете вы, кнопкой**, см. «Выкатить на прод» ниже. Так на прод попадает только версия, которая уже прошла стенд.

После каждого push в ветку `main`:

1. GitHub Actions собирает образ приложения и кладёт его в GitHub Container Registry (GHCR) с тегом — хешем коммита. Ход видно на GitHub во вкладке Actions → Deploy staging
2. Тот же образ выкатывается на тест-стенд. Два задания на одно окружение сразу не идут: новое ждёт, пока закончится прежнее

Выкатка на любое окружение, и со стенда, и с прода, идёт так:

1. GitHub копирует папку `deploy/` на сервер и запускает там `deploy.sh`. Новые файлы из `deploy/` попадают на сервер сами
2. Сервер проверяет `.env` окружения. Если `BETTER_AUTH_URL` не совпадает с адресом окружения или секрет входа такой же, как у другого окружения, выкатка останавливается, ничего не изменив
3. **Только прод:** сервер сохраняет бэкап базы, см. «Бэкапы базы». Не получилось — выкатка останавливается, работает прежняя версия. На стенде бэкапа нет: его база — копия прода
4. Сервер скачивает образ и отдельным разовым контейнером из него применяет миграции базы. Упали миграции — новая версия не запускается, работает прежняя. Первая выкатка со входом (миграция `0004`) отдаёт все существующие контакты, заметки и группы пользователю с почтой `OWNER_EMAIL`; если почта не задана, а контакты есть, миграция останавливается с ошибкой `OWNER_EMAIL is not set`, и база остаётся как была
5. Сервер запускает новую версию и проверяет `/health`
6. **Только прод:** сервер удаляет старые образы, см. «Старые образы»
7. В конце GitHub открывает `/health` окружения снаружи и сверяет версию

Если какой-то шаг упал, выкатка в Actions краснеет, и GitHub присылает письмо. Сам сервер ничего не откатывает: решаете вы, см. «Откат».

Какая версия сейчас работает: откройте https://app.example-crm.site/health (прод) или https://test-app.example-crm.site/health (стенд) — поле `commit` совпадает с последним коммитом в `main`. `/health` открыт без пароля и на стенде.

На сервере у каждого окружения свой проект docker compose и своя папка: `prod` в `/srv/prod`, `staging` в `/srv/staging`. База у каждого своя, и обе отдельны от базы на вашем компьютере. Логи — не больше 30 МБ на контейнер. Какие образы хранятся на сервере и в GHCR — см. «Старые образы».

Что где:

- `Dockerfile` — как собирается приложение
- `.github/workflows/deploy.yml` — Deploy staging: после merge в `main` сборка, GHCR, выкатка на стенд
- `.github/workflows/deploy-prod.yml` — Deploy prod: выкатка и откат прода по кнопке, чистка GHCR
- `deploy/ci-resolve-sha.sh` — выбирает версию для Deploy prod и проверяет, что она прошла стенд
- `deploy/ci-deploy.sh` — копирует `deploy/` на сервер, запускает выкатку или откат и проверяет адрес снаружи
- `deploy/ci-prune-ghcr.sh` — удаляет старые образы в GHCR
- `deploy/deploy.sh <окружение> …` — выкатка на стороне сервера (бэкап на проде, миграции, запуск, чистка образов), откат, бэкап и состояние. Окружение — `prod` или `staging`, первым словом
- `deploy/restore.sh` — восстановление базы из бэкапа, запускаете только вы
- `deploy/lib.sh` — общие части `deploy.sh` и `restore.sh`
- `deploy/compose.yaml` — приложение и его база на сервере
- `deploy/setup-server.sh` — подготовка сервера для прода, запускаете вы с паролем sudo
- `deploy/setup-daily-backup.sh` — ночной бэкап прода (таймер systemd), запускаете вы с паролем sudo
- `deploy/setup-staging.sh` — подготовка сервера для тест-стенда, запускаете вы с паролем sudo

### Выкатить на прод

Только вы и только кнопкой:

1. Откройте https://github.com/vsmortimer/personal-crm/actions/workflows/deploy-prod.yml
2. Справа нажмите **Run workflow**. Ветка — `main`
3. Поле `sha` оставьте пустым: выкатится версия последней зелёной выкатки на тест-стенд. Галочку `rollback` не ставьте
4. Нажмите зелёную **Run workflow** и откройте появившийся запуск **Deploy prod**
5. Дождитесь зелёных заданий `deploy` и `prune-ghcr`. Внизу страницы запуска, в итогах (Summary), написано, какой SHA выкатился и какой работал до него

Как проверить: https://app.example-crm.site/health — поле `commit` совпадает с SHA из итогов запуска. Откройте https://app.example-crm.site и войдите: контакты на месте.

Что ещё нужно знать:

- Версия, которой не было на стенде, на прод не поедет: запуск остановится с понятным текстом. Хотите выкатить конкретный коммит — впишите его полный хеш (40 символов) в поле `sha`; он всё равно должен пройти стенд
- Красное задание `deploy` — выкатка упала. Какой шаг красный и почему, написано в его логе. Сервер ничего сам не откатывает: решаете вы, при необходимости — «Откатить на прошлую версию» ниже
- Красное только `prune-ghcr` — выкатка прошла, не получилась чистка старых образов в GHCR. Прод работает, на следующей выкатке чистка повторится

### Откатить на прошлую версию

Откат нужен, когда новая версия на проде работает плохо. Он возвращает версию, которая работала до последней выкатки (её образ хранится на сервере):

1. Откройте https://github.com/vsmortimer/personal-crm/actions/workflows/deploy-prod.yml → **Run workflow**
2. Поставьте галочку `rollback`, поле `sha` оставьте пустым. Тест-стенд при откате не проверяется
3. Нажмите **Run workflow**. Задание `deploy` зелёное — откат прошёл. В итогах запуска написано, какая версия работает теперь и какая была до неё

Как проверить: https://app.example-crm.site/health — `commit` равен SHA из итогов. Миграции базы при откате не отменяются, детали и исключение для выкатки входа — в «Откат» ниже. Чтобы снова поехать вперёд — обычный запуск с пустым `sha`.

### Команды на сервере

Вставлять в Терминал на Mac. Каждая просит пароль sudo: символы при вводе не видны, это нормально.

- Состояние прода и список бэкапов: `ssh -t crm sudo -u crmdeploy bash /srv/prod/deploy/deploy.sh prod status`
- Состояние стенда: `ssh -t crm sudo -u crmdeploy bash /srv/staging/deploy/deploy.sh staging status`
- Бэкап базы прода прямо сейчас: `ssh -t crm sudo -u crmdeploy bash /srv/prod/deploy/deploy.sh prod backup`
- Тестовые данные в пустую базу: `ssh -t crm sudo -u crmdeploy bash /srv/prod/deploy/deploy.sh prod seed`
- Настройки базы и входа лежат в `/srv/prod/.env`, прочитать их может только пользователь crmdeploy: `ssh -t crm sudo -u crmdeploy nano /srv/prod/.env`

### Вход и письма на сервере

На сервере письма со ссылками для входа уходят настоящие, через сервис Resend по SMTP. В `/srv/prod/.env` должны быть пять строк (без них выкатка остановится на первом шаге, ничего не изменив):

```
BETTER_AUTH_SECRET=случайная строка
BETTER_AUTH_URL=https://app.example-crm.site
SMTP_URL=smtps://resend:КЛЮЧ_API@smtp.resend.com:465
MAIL_FROM="Личная CRM <noreply@mail.crm.app.example-crm.site>"
OWNER_EMAIL=ваша почта
```

- `BETTER_AUTH_SECRET` - своя случайная строка для сервера (не та, что на вашем компьютере): `openssl rand -base64 32`
- `SMTP_URL` - `КЛЮЧ_API` замените ключом из Resend. Если у ключа есть символы вроде `/` или `@`, перекодируйте их в `%2F` и `%40`
- `OWNER_EMAIL` - ваша настоящая почта, с неё всё и начинается: ей достаются контакты, которые были до входа

Resend настраивается один раз, до первой выкатки со входом:

1. Заведите аккаунт на https://resend.com
2. В разделе Domains добавьте домен `mail.crm.app.example-crm.site`. Resend покажет записи DNS - добавьте их у регистратора домена. Домен должен получить статус Verified
3. В разделе API Keys создайте ключ с правом отправки писем. Он показывается один раз - сразу вставьте его в `SMTP_URL`
4. Проверьте письмо: в панели Resend отправьте тестовое письмо на свою почту
5. С сервера проверьте, что порт 465 открыт: `ssh crm nc -vz smtp.resend.com 465`. Должно быть `succeeded`. Если порт закрыт, у Resend есть порты 2465 и 587: в `SMTP_URL` замените `smtps://` на `smtp://` и `465` на `2465` или `587`

Как проверить после выкатки: https://app.example-crm.site открывает страницу входа → ваша почта → письмо приходит в настоящий ящик → внутри все прежние контакты, их столько же, сколько было → другая почта → «Контактов пока нет». Письма нет - смотрите журнал приложения: `ssh -t crm sudo -u crmdeploy docker logs --tail 80 prod-app-1`

### Тест-стенд

Вторая копия приложения на том же сервере: https://test-app.example-crm.site. На ней проверяют новую версию, не трогая прод. Что в ней устроено:

- у стенда свои база, `.env` и ключи; общего с продом у него только сервер и образ приложения
- сайт закрыт паролем (логин `staging`). Без пароля открывается только `/health`: по нему GitHub проверяет, что выкатка прошла
- база стенда — копия данных прода из его последнего бэкапа. Испортилась — пересоздайте из свежего бэкапа (команда ниже)
- письма со ссылкой для входа настоящие, со своим ключом почты. Ссылка в письме ведёт на адрес того окружения, где запросили вход: со стенда — на `test-app`, с прода — на `app`
- кука входа живёт только на своём адресе, без общего домена: войти на стенде не значит войти на проде, и наоборот
- контейнеры стенда ограничены по памяти: приложение 320 МБ, база 192 МБ. У прода лимитов нет
- на стенде лежат настоящие данные ваших знакомых. Пароль — единственная защита, держите его в секрете

**Первый запуск** (один раз):

1. **Адрес.** У регистратора домена добавьте запись A: имя `test-app`, значение — тот же IP, что у `app.example-crm.site`. Пока записи нет, шаг 2 остановится и скажет, что делать
2. **Подготовка сервера.** Вставьте в Терминал на Mac, по одной строке (первая — из папки проекта). Просит пароль sudo, потом пароль стенда: придумайте не короче 12 символов, при вводе символы не видны:

   ```
   scp deploy/* crm:crm-app-setup/
   ssh -t crm sudo bash crm-app-setup/setup-staging.sh
   ```

   Успех — `ALL DONE` в конце и две строки с кодами ответа: адрес `/` отвечает `401` (спрашивает пароль), `/health` пока `502` (приложения ещё нет)

3. **Настройки стенда.** Откройте файл командой `ssh -t crm sudo -u crmdeploy nano /srv/staging/.env` и вставьте семь строк, подставив свои значения. Сохранить: Ctrl+O, Enter, выйти: Ctrl+X:

   ```
   POSTGRES_USER=crm
   POSTGRES_PASSWORD=случайная строка
   POSTGRES_DB=crm
   BETTER_AUTH_SECRET=случайная строка, не такая, как на проде
   BETTER_AUTH_URL=https://test-app.example-crm.site
   SMTP_URL=smtps://resend:КЛЮЧ_API_СТЕНДА@smtp.resend.com:465
   MAIL_FROM="Личная CRM (тест) <noreply@mail.crm.app.example-crm.site>"
   OWNER_EMAIL=ваша почта
   ```

   Случайные строки: `openssl rand -hex 24` для пароля базы и `openssl rand -base64 32` для `BETTER_AUTH_SECRET`. Ключ для `SMTP_URL` — отдельный, новый, из раздела API Keys в Resend (тот же домен, что у прода). Пока строки неверные, выкатка стенда остановится на первом шаге, ничего не изменив

4. **Первая выкатка.** После merge в `main` в Actions → Deploy staging пройдёт задание `deploy-staging`. Стенд откроется с пустой базой
5. **Данные прода на стенд:**

   ```
   ssh -t crm sudo -u crmdeploy bash /srv/staging/deploy/deploy.sh staging refresh-db
   ```

   Команда показывает, какой бэкап прода загрузит и какую базу стенда заменит, и ждёт `yes`. Потом останавливает приложение стенда, создаёт базу заново, загружает бэкап, применяет миграции и запускает ту же версию. Прод она не трогает, только читает его бэкапы. Её же запускают, когда база стенда испортилась

**Как проверить, что стенд работает:**

1. https://test-app.example-crm.site спрашивает логин и пароль; с неверным паролем — отказ
2. https://test-app.example-crm.site/health открывается без пароля, `commit` совпадает с последним коммитом в `main`
3. Введите логин и пароль, затем свою почту на странице входа. Письмо приходит, ссылка в нём начинается с `https://test-app.example-crm.site/`. После `refresh-db` внутри те же контакты, что были на проде в последнем бэкапе
4. Кука: Chrome → F12 → Application → Cookies → `https://test-app.example-crm.site`. У куки сессии в колонке Domain — `test-app.example-crm.site`, без точки впереди. В `app.example-crm.site` вы при этом не вошли
5. Память: `ssh -t crm sudo docker stats --no-stream` — у контейнеров `staging-app-1` и `staging-db-1` в колонке MEM USAGE / LIMIT лимиты `320MiB` и `192MiB`

**Если выкатка на стенд упала.** Задание `deploy-staging` в Actions красное. Прод это не трогает: он выкатывается только по кнопке, и Deploy prod без поля `sha` возьмёт последнюю версию, которая прошла стенд. Журнал приложения: `ssh -t crm sudo -u crmdeploy docker logs --tail 80 staging-app-1`. Предыдущую версию стенда запускает `ssh -t crm sudo -u crmdeploy bash /srv/staging/deploy/deploy.sh staging rollback`. Сам сервер ничего не откатывает.

**Сменить пароль стенда:** `ssh -t crm sudo CHANGE_PASSWORD=yes bash crm-app-setup/setup-staging.sh` (файлы из шага 2 уже на сервере).

### Откат

Основной способ — кнопка, см. «Откатить на прошлую версию» выше. Запасной, если Actions недоступен, — команда на сервере. Она запускает ту же версию, которая работала до последней выкатки:

```
ssh -t crm sudo -u crmdeploy bash /srv/prod/deploy/deploy.sh prod rollback
```

Откат всегда возможен: образ предыдущей версии прода сервер не удаляет.

Миграции базы при откате не отменяются: прежняя версия продолжает работать с новой схемой базы.

Откат не трогает данные. Вернуть базу к прежнему состоянию — это восстановление из бэкапа, см. ниже.

**Исключение — откат выкатки входа.** Она добавила контактам и группам владельца (`user_id`), а прежняя версия про него не знает: читать контакты она может, но добавить контакт - нет. Поэтому после выкатки входа откатывают только вместе с базой и строго в таком порядке:

1. `ssh -t crm sudo -u crmdeploy bash /srv/prod/deploy/deploy.sh prod rollback` - запускает прежнюю версию
2. `restore.sh` с бэкапом, снятым перед выкаткой входа, см. «Восстановление базы из бэкапа». Скрипт применяет миграции **работающей** версии, а это уже прежняя, без входа

В обратном порядке нельзя: если восстановить базу при новой версии, скрипт снова применит миграции входа. Бэкап перед выкаткой входа - тот, чьё имя заканчивается хешем версии, которая работала до неё (на момент выкатки это самый свежий в списке). Бэкапов «перед выкаткой» хранятся только 7 последних: если с выкатки входа прошло больше семи выкаток, этого бэкапа уже нет, и так откатить не получится.

Что при этом пропадёт: всё, что появилось после выкатки входа, — аккаунты друзей и их контакты, ваши новые контакты и заметки. Приложение снова открывается без входа, а контакты, заметки и группы такие, какими были до выкатки.

### Бэкапы базы

Бэкапы базы прода лежат в `/srv/prod/backups/`. Их снимает сервер:

- **каждую ночь в 03:00 по Москве** — таймер systemd `crm-backup` (ставит `setup-daily-backup.sh`, см. «Подготовка сервера»); имя файла заканчивается на `-daily.dump`
- **перед каждой выкаткой на прод**
- **перед восстановлением** из бэкапа — с окончанием `-before-restore`

В имени файла — когда снят бэкап и какая версия приложения работала в этот момент (при выкатке — версия до неё):

```
20261107-153012-d582f1d4fefffc741b0d026fb2285459827c9850.dump
20261108-030000-d582f1d4fefffc741b0d026fb2285459827c9850-daily.dump
```

Здесь `20261107-153012` — 7 ноября 2026, 15:30:12 по времени сервера, дальше — хеш коммита версии.

- Хранятся 7 последних ночных бэкапов и отдельно 7 последних остальных (перед выкаткой и перед восстановлением). Более старые удаляет сервер сам
- Прочитать их может только пользователь crmdeploy
- Список бэкапов показывает `deploy.sh prod status` (внизу) и `restore.sh` без имени файла
- Бэкапы лежат на том же сервере, что и база: если сервер пропадёт, пропадут и они

**Как проверить, что ночной бэкап работает:**

1. `ssh -t crm sudo systemctl list-timers crm-backup.timer` — в колонке NEXT ближайшие 03:00 по Москве (на сервере время может показываться в другом поясе: это то же время)
2. `ssh -t crm sudo journalctl -u crm-backup --no-pager -n 30` — что делал таймер; успешный запуск заканчивается строкой `saved … -daily.dump`
3. `ssh -t crm sudo -u crmdeploy bash /srv/prod/deploy/deploy.sh prod status` — в списке внизу самый свежий `-daily.dump` с сегодняшней или вчерашней датой

Упавший ночной бэкап письма не присылает: он виден только в журнале и по дате самого свежего файла, поэтому заглядывайте в список время от времени.

Копии, которые снимает `setup-server.sh`, лежат отдельно — в `/var/backups/personal-crm/`, прочитать их может только root, сами они не удаляются.

### Восстановление базы из бэкапа

Только вручную и только скриптом `restore.sh`. Он заменяет всю базу прода содержимым бэкапа: всё, что добавлено после бэкапа, из базы пропадёт. Но перед заменой скрипт сохраняет копию текущей базы, и к ней можно вернуться тем же способом.

Версия приложения при этом не меняется. Бэкап обычно снят при прежней версии, поэтому после загрузки скрипт применяет миграции работающей версии — так же, как выкатка. Данные из бэкапа остаются.

**1. Выберите бэкап.** Вставьте в Терминал на Mac (строка вида `viktor@…`) и нажмите Enter:

```
ssh -t crm sudo -u crmdeploy bash /srv/prod/deploy/restore.sh
```

Появится `[sudo] password for crmapp:` — введите пароль sudo и нажмите Enter. Символы при вводе не видны, это нормально. Скрипт покажет список бэкапов, сверху самые новые, и ничего не изменит. Скопируйте имя нужного файла.

**2. Запустите восстановление**, подставив имя файла вместо `ИМЯ_ФАЙЛА`:

```
ssh -t crm sudo -u crmdeploy bash /srv/prod/deploy/restore.sh ИМЯ_ФАЙЛА
```

**3. Проверьте, что собирается сделать скрипт.** Пока ничего не изменилось, он показывает:

```
=== Restore replaces the whole production database
backup:          /srv/prod/backups/20261107-153012-d582f1d….dump
                 180K, saved 2026-11-07 15:30, tables with data: 6
data of version: d582f1d…
replaces:        database … of compose project prod: it is dropped and created again
rows in it now:
                 public.contacts 1004
                 public.notes 1586
                 …
app version:     …, stays the same; its migrations run after the backup is loaded
before anything changes, the current database is saved to /srv/prod/backups

Type yes to replace the database, anything else to stop:
```

- `backup` — какой файл загрузится, его размер и когда он снят
- `data of version` — при какой версии приложения снят бэкап
- `replaces` — какая база будет удалена и создана заново
- `rows in it now` — сколько строк в таблицах базы сейчас
- `app version` — версия приложения, она останется той же

Всё верно — напечатайте `yes` и нажмите Enter. Любой другой ответ — скрипт напишет `Nothing changed` и закончит, база не изменится.

Пока скрипт ждёт ответа, выкатки ждут его. Не оставляйте вопрос дольше 15 минут: выкатка, которая ждала дольше, упадёт, её можно запустить заново в Actions.

**4. Дождитесь конца.** Скрипт сохраняет копию текущей базы, останавливает приложение, удаляет базу, создаёт её заново, загружает бэкап, применяет миграции и запускает ту же версию приложения. Около минуты сайт отвечает ошибкой 502. Успех — в конце:

```
=== Rows after the restore
  public.contacts …
  public.notes …

=== Done: the database holds ИМЯ_ФАЙЛА, … is live
```

**Как проверить:** откройте https://app.example-crm.site — контакты и заметки такие, какими были в момент бэкапа. На https://app.example-crm.site/health поле `commit` то же, что до восстановления.

**Если что-то упало**, в конце будет `RESTORE FAILED:` — что осталось после сбоя (например, приложение остановлено), и имя копии базы, снятой перед восстановлением. Сам скрипт ничего не возвращает. Решаете вы: чтобы вернуть базу как была до восстановления, запустите ту же команду из шага 2 с именем этой копии — оно напечатано в строке `To load it back`.

Восстановить копию от `setup-server.sh`: сначала положите её к остальным бэкапам, подставив имя файла:

```
ssh -t crm sudo install -o crmdeploy -g crmdeploy -m 600 /var/backups/personal-crm/ИМЯ_ФАЙЛА /srv/prod/backups/
```

В имени такой копии нет версии, поэтому в строке `data of version` будет `not in the file name`. Восстанавливайте её сразу: следующая выкатка может удалить её как старую — в `/var/backups/personal-crm/` оригинал останется.

### Старые образы

- **На сервере** после каждой удачной выкатки на прод удаляются образы старше 2 недель (от даты сборки). Остаются в любом случае две последние версии прода (текущая и та, куда ведёт откат) и текущая версия стенда
- **В GHCR** после каждой удачной выкатки на прод (задание `prune-ghcr`) остаются 10 последних сборок, старшие удаляются. Только что выкатанная версия не удаляется никогда. Откату это не мешает: он берёт образ с сервера. Но версию, которой уже нет и в GHCR, и на сервере, выкатить нельзя

### Подготовка сервера

Файлы из `deploy/` выкатка копирует на сервер сама. Но пользователей, права и nginx настраивает только `setup-server.sh` (прод) и `setup-staging.sh` (тест-стенд, см. «Тест-стенд»), и запускаете их вы — первый раз и когда файл поменялся. Для прода:

```
scp deploy/* crm:crm-app-setup/
ssh -t crm sudo bash crm-app-setup/setup-server.sh
```

Ночной бэкап ставится отдельно, **после первого Deploy prod** с этой доработкой (он привозит на сервер команду `backup`):

```
scp deploy/* crm:crm-app-setup/
ssh -t crm sudo bash crm-app-setup/setup-daily-backup.sh
```

Успех — `ALL DONE` в конце; перед ним строка `saved … -daily.dump` (пробный бэкап) и таймер `crm-backup.timer` с ближайшим запуском.

GitHub заходит на сервер своим ключом как пользователь crmdeploy. Ключ лежит в секретах репозитория (Settings → Secrets and variables → Actions: `DEPLOY_SSH_KEY`, `DEPLOY_KNOWN_HOSTS`, `DEPLOY_HOST`). crmdeploy может копировать файлы и запускать Docker, а это уровень root на сервере. Поэтому ключ хранится только в секретах GitHub.

## Для разработки

- `pnpm build` и `pnpm start` — собрать и запустить «боевую» версию (быстрее, чем `pnpm dev`)
- `pnpm lint` — проверка кода
- `pnpm format` — отформатировать код Prettier; `pnpm format:check` — только проверить
- `pnpm typecheck` — проверка типов TypeScript
- `pnpm test` — тесты, см. «Тесты»
- `pnpm test:e2e` — сквозные тесты в браузере, см. «Сквозные тесты (e2e)»
- `pnpm db:generate` — создать миграцию после изменения схемы в `src/db/schema.ts`
- `pnpm db:migrate` — применить миграции к базе; если в базе есть контакты, нужен `OWNER_EMAIL` в `.env`
- `pnpm db:seed` — заполнить демо-данными пользователя с почтой `OWNER_EMAIL`
