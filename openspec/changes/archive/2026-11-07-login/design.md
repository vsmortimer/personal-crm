# Design

## Context

Зачем фича - см. proposal.md, раздел Why. Что должно получиться - `specs/user-auth/spec.md`, `specs/data-ownership/spec.md` и изменение в `specs/contact-groups/spec.md`.

Как устроено сейчас:

- Входа нет. Любой, кто открыл адрес, видит все контакты. Таблицы `contacts`, `notes`, `groups`, `contact_groups` (`src/db/schema.ts`) без владельца. Уникальность названия группы - индекс `groups_name_lower_idx` по `lower(name)` на всю базу.
- Все запросы к базе - в `src/lib/contacts.ts` и `src/lib/groups.ts`, их вызывают страницы (серверные компоненты) и действия в `src/app/actions.ts`. Каждый запрос начинается с `connection()`, страницы с данными обёрнуты в `Suspense` (Next 16, `cacheComponents`).
- Несуществующий контакт: `notFound()` → общий `src/app/not-found.tsx` с заголовком «Такой страницы нет». «Контакт не найден» - только в `<title>`.
- Миграции применяет `src/db/migrate.ts`, одним соединением. На сервере - разовым контейнером до старта нового образа, после бэкапа (`deploy/deploy.sh`). `restore.sh` после загрузки бэкапа применяет миграции работающей версии тем же скриптом.
- Тесты: Vitest на настоящем Postgres в своей базе `_test` (подменён только `connection()`), Playwright на собранном приложении и базе `_e2e_test`. В CI у обоих jobs - Postgres как service container.
- Настройки приходят из `.env` (`@next/env`), на сервере - `/srv/prod/.env` через `deploy/compose.yaml`. Образ один для всех, `next build` собирается с подставными `POSTGRES_*`.
- nginx на сервере проксирует `app.example-crm.site` на `127.0.0.1:3000`. Для приложения все запросы приходят с одного адреса.
- Better Auth 1.7.18 - последняя стабильная на 2026-11-07. Что проверено по её коду: ссылка MagicLink одноразовая, срок проверяется при входе, почта при создании пользователя и при поиске приводится к маленьким буквам. Новая ссылка старые **не** отменяет. Встроенный лимит - по IP, а не по почте. `disabledPaths` закрывает путь только для HTTP, вызовы `auth.api.*` с сервера работают.

## Goals / Non-Goals

**Goals:**

- Одна точка входа в отправку письма - серверное действие. Через неё проходят и проверка почты, и лимит, и отмена старых ссылок, обойти её HTTP-запросом нельзя.
- Владелец проверяется в самом запросе к базе, а не в интерфейсе: каждая функция в `src/lib/contacts.ts` и `src/lib/groups.ts` получает `userId` и без него не работает.
- Существующие данные получают владельца внутри той же миграции, в одной транзакции. Ошибка - и база остаётся как была.
- Куда уходят письма, решает только `SMTP_URL`. Сборка одна и та же.

**Non-Goals:**

- Row Level Security в Postgres. Это сильнее, но требует ставить пользователя на каждое соединение из пула. Хватит фильтра в каждом запросе и тестов на него.
- Клиентская библиотека Better Auth (`better-auth/react`): все формы - серверные действия, браузеру она не нужна.
- Очистка старых строк лимита и просроченных ссылок по расписанию. Строки одной почты чистятся при её следующем запросе, остальных мало.

## Decisions

### 1. Better Auth на сервере: один модуль `src/lib/auth.ts`

`betterAuth({...})` с такими настройками:

- `database: drizzleAdapter(db, { provider: "pg", usePlural: true, schema })`. Таблицы `users`, `sessions`, `accounts`, `verifications` - во множественном числе, как `contacts` и `groups`. Слово `user` в Postgres зарезервировано.
- `plugins: [magicLink({ expiresIn: 15 * 60, storeToken: "hashed", sendMagicLink }), nextCookies()]`. Хеш токена в базе: даже тот, кто прочитал базу, не войдёт по чужой ссылке.
- `session: { expiresIn: 30 дней, updateAge: 1 час }`. Срок сдвигается на 30 дней вперёд, когда сессия старше часа с прошлого продления.
- `disabledPaths: ["/sign-in/magic-link"]`. HTTP-путь отправки ссылки закрыт (404), письмо можно запросить только через действие из решения 3.
- `rateLimit: { enabled: false }`. Встроенный лимит считает по IP. За nginx у всех один IP, и он ограничивал бы всех пользователей сразу. Лимит по почте - наш, решение 3. Подобрать токен из 32 случайных символов перебором нельзя.
- `secret` и `baseURL` - из `BETTER_AUTH_SECRET` и `BETTER_AUTH_URL` во время работы, не при сборке.
- Пароли не включены, соцсети тоже.

Обработчик `src/app/api/auth/[...all]/route.ts` (`toNextJsHandler`). Нужен для ссылки из письма и выхода.

Другие варианты: Auth.js или свой вход - нет, Better Auth и MagicLink заданы спекой.

### 2. Таблицы и владелец

- Таблицы Better Auth пишем руками в `src/db/schema.ts` по её схеме: `id` - текст, его создаёт Better Auth. Колонки - snake_case, как в остальной схеме.
- `login_link_requests`: `id`, `email`, `created_at`, индекс `(email, created_at)`. Одна строка - одно ушедшее письмо, для лимита.
- `contacts.user_id` и `groups.user_id` - `text not null`, ссылка на `users.id` без каскада. Случайное удаление пользователя не унесёт его контакты, база не даст. Индекс `contacts(user_id)`.
- Уникальность групп: индекс `groups_user_id_name_lower_idx` по `(user_id, lower(name))` вместо `groups_name_lower_idx`. «Друзья» может быть у каждого пользователя.
- У `notes` и `contact_groups` своего владельца нет: заметка принадлежит владельцу контакта, связь - владельцу контакта и группы. Запросы проверяют владельца через контакт или группу.

Другой вариант: `user_id` и в `notes` - дублирование, которое может разойтись с контактом. Не нужно, заметки всегда читаются через контакт.

### 3. Запрос ссылки: `requestLoginLink(rawEmail, headers)` в `src/lib/login-link.ts`

Действие `requestLoginLinkAction` в `src/app/login/actions.ts` только читает поле и вызывает эту функцию. Шаги:

1. Почта: `trim()`, `toLowerCase()`, проверка `z.email()` и не длиннее 254 - те же правила, что у почты контакта. Не прошла - `{ error: "Проверь адрес почты" }`, в базу ничего не пишется.
2. Транзакция с `pg_advisory_xact_lock(hashtext(email))`: два запроса одной почты идут по очереди.
3. Удалить строки этой почты из `login_link_requests` старше 10 минут, посчитать оставшиеся. Уже 3 - `{ error: "Слишком часто, попробуй через несколько минут" }`.
4. Удалить из `verifications` прежние ссылки этой почты: `identifier like 'magic-link:%' and value::jsonb->>'email' = email`. Старые ссылки перестают работать.
5. Записать строку в `login_link_requests`.
6. `auth.api.signInMagicLink({ body: { email, callbackURL: "/", errorCallbackURL: "/login/expired" }, headers })`. Better Auth создаёт ссылку и вызывает `sendMagicLink` → письмо (решение 4).
7. Письмо не ушло - транзакция откатывается: строка лимита пропадает, прежние ссылки возвращаются. Ответ - `{ error: "Не удалось отправить письмо, попробуй ещё раз" }`. Ушло - `{ sentTo: email }`.

Транзакция открыта, пока уходит письмо, около секунды. Для личного приложения это не проблема, зато лимит и «новая ссылка отменяет старые» верны и при двух одновременных запросах.

Ответ не зависит от того, есть ли такой пользователь: пользователь появляется только при входе по ссылке.

### 4. Письма: Nodemailer, куда - решает `SMTP_URL`

- `src/lib/mailer.ts`: `nodemailer.createTransport(SMTP_URL)` создаётся при первой отправке. От кого - `MAIL_FROM`. Нет настройки - понятная ошибка в логе, пользователь видит «Не удалось отправить письмо…».
- `src/lib/login-email.ts`: чистая функция `loginEmail(url)` → `{ subject, html, text }`. Тема «Вход в Личную CRM», кнопка «Войти», «Ссылка работает 15 минут.», «Если вы не запрашивали вход - просто проигнорируйте письмо». Есть и текстовая версия, для почтовых программ без HTML.
- Цвета и шрифты в письме - inline-стили. Почтовые программы не понимают CSS-переменные, поэтому значения скопированы из `src/app/tokens.css` в одну константу рядом, с комментарием, откуда они. Это единственное место, где токены повторены значениями.
- Настройки:
  - у меня и в тестах: `SMTP_URL=smtp://127.0.0.1:1025` - Mailpit;
  - на сервере: `SMTP_URL=smtps://resend:<ключ>@smtp.resend.com:465` - Resend по SMTP;
  - везде: `MAIL_FROM="Личная CRM <noreply@mail.crm.app.example-crm.site>"`.

Другой вариант: SDK Resend на сервере и Nodemailer локально - две ветки кода, а спека требует одну библиотеку и одну сборку.

### 5. Вход по ссылке и устаревшая ссылка

Ссылка в письме: `BETTER_AUTH_URL/api/auth/magic-link/verify?token=…&callbackURL=/&errorCallbackURL=/login/expired`. Better Auth сам:

- проверяет и сразу удаляет токен: второй раз ссылка не сработает;
- новая почта - создаёт пользователя (`name` пустой, `email_verified` да);
- создаёт сессию, ставит cookie и переводит на `/`.

Просроченный, использованный или отменённый токен - переход на `/login/expired?error=…`. Страница `src/app/login/expired/page.tsx` всегда показывает «Ссылка устарела, запроси новую» и кнопку-ссылку «На страницу входа» (`/login`), что бы ни было в `error`.

### 6. Кто вошёл: `src/lib/session.ts` и `src/proxy.ts`

- `getCurrentUser()` - `cache()` вокруг `auth.api.getSession({ headers: await headers() })`: один запрос к базе на всю отрисовку. `requireUser()` - то же, а без входа `redirect("/login")`.
- Страницы, шапка и **каждое** действие в `src/app/actions.ts` первым делом вызывают `requireUser()` и передают `user.id` в функции из `src/lib`. Сами функции сессию не читают: в них всё видно явно, и их легко проверять в Vitest.
- `src/proxy.ts` (в Next 16 это бывший middleware, работает в Node.js). Не трогает `/api/auth/*`, `/health`, `/_next/*` и `favicon.ico`. Для GET и HEAD:
  - вызывает `auth.api.getSession({ headers, returnHeaders: true })`;
  - нет входа и это не `/login…` - переводит на `/login`;
  - вход есть и это `/login` - переводит на `/`;
  - иначе пропускает дальше и передаёт браузеру `Set-Cookie` от Better Auth.
- Остальные запросы, это вызовы серверных действий, proxy пропускает. Их проверяет `requireUser()` внутри действия, как советует документация Next: proxy - не единственная защита.

Зачем запрос к базе в proxy, хотя документация Next советует проверять там только cookie. Серверный компонент не может записать cookie. Продлить cookie при обычном заходе можно только здесь, иначе браузер забудет вход через 30 дней после входа, даже если я захожу каждый день. Запрос - один, по индексу, пользователей единицы.

Другой вариант: клиентский компонент в шапке, который на каждой странице дёргает `/api/auth/get-session`. Это лишний JavaScript и лишний запрос, и без JavaScript вход не продлевается.

Проверить при реализации: `nextCookies()` пропускает продление в запросах с заголовком `RSC: 1`. Если из-за этого proxy не продлевает cookie при переходах внутри приложения, продление в proxy делаем без этого плагина, а cookie при выходе снимаем сами.

### 7. Выход

`signOutAction` в шапке: `auth.api.signOut({ headers })` удаляет только сессию этого устройства, `nextCookies()` снимает cookie, затем `redirect("/login")`. Другие устройства остаются внутри: у каждого своя строка в `sessions`.

### 8. Только своё в каждом запросе

- `listContacts(userId, query, groupId)`, `listDueContacts(userId, now?)`, `getContact(userId, id)`, `listNotes(userId, contactId)`, `countNotes(userId, contactId)`, `createContact(userId, …)`, `updateContact(userId, id, …)`, `deleteContact(userId, id)`, `addNote(userId, contactId, body)`. Всё, что читает или меняет контакт, добавляет `contacts.user_id = userId`. Заметки - через контакт этого пользователя.
- `listGroups(userId)`, `listContactGroups(userId, contactId)`, `renameGroup(userId, id, name)`, `deleteGroup(userId, id)` - с `groups.user_id = userId`. «Название занято» ищется только среди своих групп.
- `setContactGroups(tx, userId, contactId, …)`: новые группы создаются с `user_id`, `on conflict` - по новому индексу. Отмеченные `groupIds` берутся только из своих групп, чужой номер молча отбрасывается (сценарий «Свой контакт в чужую группу»).
- Чужая запись выглядит так же, как несуществующая: `null` или `false`, а дальше - уже готовые тексты «Контакт не найден: возможно, его уже нет в базе.» и «Группа не найдена: …».
- Страница «Контакт не найден»: `src/app/contacts/[id]/not-found.tsx`. Ловит `notFound()` из карточки и из формы «Изменить». Заголовок «Контакт не найден», строка «Возможно, его удалили или ссылка набрана с ошибкой.», кнопка «К списку контактов». Общий `src/app/not-found.tsx` не меняется.

### 9. Две миграции: `0003` - таблицы входа, `0004` - владелец для существующих данных

- `0003` только добавляет таблицы `users`, `sessions`, `accounts`, `verifications`, `login_link_requests`. Существующие данные не трогает.
- `0004` даёт владельца контактам и группам. Это отдельный шаг реализации (tasks.md, группа 6), поэтому и отдельный файл. На сервере обе применятся одной выкаткой, в одной транзакции.

`0004`: `pnpm db:generate` создаёт файл, дальше правим его руками. drizzle-kit сразу сделал бы `user_id not null`, а это упадёт на существующих строках. Порядок в файле:

1. `user_id` в `contacts` и `groups` - пока может быть пустым.
2. Блок `DO $$ … $$`: если в `contacts` или `groups` есть строки, берёт почту из `current_setting('crm.owner_email', true)`. Пусто - `raise exception 'OWNER_EMAIL is not set: existing contacts and groups need an owner'`. Иначе создаёт пользователя с этой почтой, если его нет (`id = gen_random_uuid()::text`, `name = ''`, `email_verified = true`), и ставит его `id` во все строки.
3. `user_id` - `not null`, ссылки на `users`, индекс по контактам, замена индекса уникальности групп.

`src/db/migrate.ts` читает `OWNER_EMAIL`, приводит к виду, как при входе (пробелы, маленькие буквы), проверяет как почту. Неверная почта - ошибка до миграций. Затем на том же единственном соединении выполняет `select set_config('crm.owner_email', $1, false)` и только потом `migrate()`. drizzle применяет все новые миграции в одной транзакции: исключение откатывает всё, и выкатка останавливается до старта новой версии.

Пустая база (новые тестовые базы, `createTestDatabase`) - блок ничего не делает, почта не нужна.

Другие варианты: почта прямо в SQL - она попала бы в публичный репозиторий (владелец выбрал `.env`). Отдельный скрипт после миграций - между ним и миграцией в базе были бы строки без владельца, и `not null` пришлось бы ставить третьим шагом.

Миграцию `0004` показать владельцу до merge (правило `CLAUDE.md`).

### 10. Демо-данные

`src/db/seed.ts` требует `OWNER_EMAIL`. Находит или создаёт пользователя с этой почтой, раскладывает контакты и группы на него. Пропускает заполнение, если у этого пользователя уже есть контакты. Данные других пользователей не мешают.

### 11. Экраны

- `/login` (`src/app/login/page.tsx`), заголовок «Вход». Клиентская форма `LoginForm` с `useActionState`: поле «Почта» (`type="email"`, `autoComplete="email"`, форма с `noValidate`, чтобы показывался наш текст, а не подсказка браузера), кнопка «Получить ссылку». Ошибка почты - под полем (`aria-invalid`, `aria-describedby`). «Ссылка для входа отправлена на …», «Слишком часто…» и «Не удалось отправить…» - под кнопкой, с `role="status"` или `role="alert"`. Форма остаётся на месте, значение поля сохраняется.
- Шапка в `src/app/layout.tsx`: справа серверный `UserMenu` в `Suspense` - почта и кнопка «Выйти» (форма с `signOutAction`). Без входа его нет, остаётся только логотип. На узком экране почта обрезается многоточием, кнопка видна всегда.
- Подсказка пустого списка на главной: строка «Добавьте первого человека, чтобы не потерять с ним связь.» меняется на «Добавь первый контакт».
- Только дизайн-токены и компоненты shadcn/ui, которые уже есть (`Input`, `Button`, `Field`, `Card`).

### 12. Mailpit и тесты

- `compose.yaml`: сервис `mail` (`axllent/mailpit`, версия - последняя стабильная при реализации, на 2026-11-07 это v1.33.0), порты `127.0.0.1:1025` (SMTP) и `127.0.0.1:8025` (страница и API). В CI - тот же образ как service container в jobs Vitest и Playwright.
- Помощник `test/mailpit.ts`: письма для адреса (`/api/v1/search?query=to:…`), письмо целиком (`/api/v1/message/{id}`), ссылка из письма, очистка (`DELETE /api/v1/messages`). Адрес - `MAILPIT_URL`, по умолчанию `http://127.0.0.1:8025`.
- Vitest: письма уходят по-настоящему в Mailpit, без подмены. Время не подменяем, а сдвигаем в базе: `expires_at` ссылки, `created_at` строк лимита, `updated_at`/`expires_at` сессии. В `test/setup.ts` перед каждым тестом очищаются и новые таблицы. Помощник `insertUser(email)`. В `actions.test.ts` подменяется только `requireUser()`: в Vitest нет запроса с cookie.
- e2e: `resetDatabase` очищает и пользователей, сессии, ссылки и лимит, создаёт владельца и его контакты, чистит Mailpit. Помощник `signIn(page, email)` проходит вход как человек: форма → письмо в Mailpit → ссылка. Главный сценарий и «Пора связаться» вызывают его перед сценарием. Главный сценарий во «втором браузере» входит под той же почтой. Новый `e2e/login.spec.ts` - критерий A и B из спеки, устаревшая ссылка, выход.
- `playwright.config.ts` и CI: `BETTER_AUTH_URL=http://127.0.0.1:3100`, тестовый `BETTER_AUTH_SECRET` (не секрет, только для тестов), `SMTP_URL=smtp://127.0.0.1:1025`, `MAIL_FROM`.

### 13. Настройки

| Настройка | У меня | На сервере |
|---|---|---|
| `BETTER_AUTH_SECRET` | случайная строка, `openssl rand -base64 32` | своя случайная строка |
| `BETTER_AUTH_URL` | `http://localhost:3000` | `https://app.example-crm.site` |
| `SMTP_URL` | `smtp://127.0.0.1:1025` | `smtps://resend:<ключ>@smtp.resend.com:465` |
| `MAIL_FROM` | `Личная CRM <noreply@mail.crm.app.example-crm.site>` | то же |
| `OWNER_EMAIL` | моя почта | моя почта |

- `.env.example` - те же ключи без значений. Если файл закрыт настройками доступа агента, агент говорит владельцу, какие строки добавить.
- `deploy/compose.yaml`: те же пять в `environment` сервиса `app` с `:?`. Без них compose падает уже на первом шаге выкатки (бэкап), ничего не меняя. Разовый контейнер миграций получает их же, `restore.sh` тоже.
- `Dockerfile`: если `next build` потребует настройки входа, их подставляют только на шаге сборки, как `POSTGRES_*`. В образ они не попадают.

## Risks / Trade-offs

- [Почтовые программы, которые заранее открывают ссылки, могут «съесть» одноразовую ссылку] → Gmail так не делает. Если увидим «Ссылка устарела» на свежей ссылке - добавим страницу с кнопкой «Войти» перед входом, отдельной правкой.
- [Хостинг закрывает исходящий порт 465] → до merge проверить с сервера `nc -vz smtp.resend.com 465`. Закрыт - у Resend есть порты 587 и 2465, меняется только `SMTP_URL`.
- [Resend не подтвердил домен отправителя - письма на сервере не уходят] → домен и записи DNS делает владелец до merge и проверяет тестовым письмом в панели Resend.
- [Новый запрос к базе забыли ограничить владельцем] → у функций `src/lib` первый аргумент - `userId`, без него код не соберётся. На каждую - тест с двумя пользователями.
- [Обычный `rollback` после этой выкатки ломает добавление контактов: в прежней версии нет `user_id`, а колонка `not null`] → в README отдельный порядок отката для этой выкатки, см. Migration Plan.
- [Запрос к базе в proxy на каждой странице] → один запрос по индексу. Для нескольких пользователей незаметно.
- [Вход по `localhost`, а ссылка ведёт на `127.0.0.1` (или наоборот) - cookie разные] → ссылка всегда на `BETTER_AUTH_URL`. В README: открывать приложение по тому же адресу.
- [Срок «30 дней» продлевается не чаще раза в час] → вход может закончиться до часа раньше. Записано в proposal, в «Решил сам».
- [Транзакция открыта, пока уходит письмо] → лимит и отмена ссылок верны при одновременных запросах. Цена - соединение занято около секунды.

## Migration Plan

До merge (только владелец, агент говорит, что именно сделать):

1. Resend: аккаунт, домен `mail.crm.app.example-crm.site`, записи DNS, ключ API.
2. В `/srv/prod/.env` (`ssh -t crm sudo -u crmdeploy nano /srv/prod/.env`) - пять строк из таблицы в решении 13, с ключом Resend и своим `BETTER_AUTH_SECRET`.
3. Агент проверяет с сервера исходящий порт 465 и показывает владельцу SQL миграции `0004`.

Выкатка - обычная: бэкап базы (с именем прежней версии) → миграции, в том числе `0003` и `0004` с владельцем → новая версия → smoke `/health`.

Проверка руками после выкатки: приложение открывает страницу входа → своя почта → письмо в настоящем ящике → внутри все прежние контакты, их число совпадает с числом до выкатки → другая почта → пустой список.

Откат - только вручную, только вместе, именно в таком порядке:

1. `deploy.sh rollback` - запускает прежнюю версию. Она пока работает с новой схемой: читать может, добавить контакт - нет.
2. `restore.sh <бэкап, снятый перед выкаткой входа>` - база как до выкатки. Скрипт применяет миграции **работающей** версии, а это уже прежняя, без `0003` и `0004`.

В обратном порядке нельзя: `restore.sh` при новой версии снова применит `0003` и `0004`. Всё, что появилось после выкатки, при откате пропадает: аккаунты друзей и их контакты, мои новые контакты и заметки. Это - в README.
